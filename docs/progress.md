### 収録リズム

**9曲。** 追加は `src/domain/patterns/` に1ファイル＋`registry.ts` に登録するだけ。

| 名前 | 拍子 | 打点（16分音符換算） | 反転 |
|---|---|---|---|
| Son Clave | 2/4 × 2 | 0 / 3 / 6 / 10 / 12 | あり |
| Rumba Clave | 2/4 × 2 | 0 / 3 / 7 / 10 / 12 | あり |
| Bossa Clave | 2/4 × 2 | 0 / 3 / 6 / 10 / 13 | あり |
| Afro Groove | 2/4 × 2 | 0 / 3 / 6（×2） | なし |
| Afro Groove2 | 2/4 × 2 | 0 / 1 / 4 / 5（×2） | なし |
| Afro Groove3 | 2/4 × 2 | 1 / 3 / 5 / 6 / 8 / 10 / 11 / 13 / 15 | なし |
| 6/8 Afro Groove 1 | 6/8 × 2 | `●・●・●●` \| `・●・●・●` | なし |
| 6/8 Afro Groove 2 | 6/8 × 2 | `●・●●・・`（×2） | なし |
| IJEXA | 2/4 × 2 | `●●・●・●●・` \| `●・●・●・●・` | なし |

2/4 は4分音符、6/8 は付点4分音符で BPM を数える。

**クラーベ3種は打点が1つずつ違う**（2026-09-07 に教則本と突き合わせて正体を確定）。

    Son Clave    0 / 3 / 6 / 10 / 12
    Rumba Clave  0 / 3 / 7 / 10 / 12   ソンの3つ目が16分ぶん後ろ
    Bossa Clave  0 / 3 / 6 / 10 / 13   ソンの5つ目が16分ぶん後ろ

`Bossa Clave` は 9/3 に「ソンでもルンバでもない」として収録したものだった。
**別途 Bossa clave を追加する必要はなかった。**

**記譜は 2/4（16分グリッド）。** 2026-09-07 に 2/2（8分グリッド）から移した。
教則本のクラーベがこの書き方のため。**鳴る音は変わっていない**
（同じリズムを違う音価で書いただけ。`bpmUnit` も 192 → 96 に合わせた）。

**`Afro Groove3` は収録で初めて周期の頭が休符から始まる。**
ハイライトの扱いがここだけ変わる（`src/domain/playhead.ts`）。

**6/8 のリズムは名前を `6/8 Afro Groove n` で揃える**（2026-08-27 オーナー判断）。

**Afro Groove2 は「カカンカカン」を2セット**（2026-08-27 オーナー確認）。
もとは1小節で書いており、鳴る音は同じだが小節線が出ず、
奏者の「2セット入る」という感じ方と合っていなかった。
口唱歌で数えると カ(48) + カン(音+間=144) = 「カカン」192 tick、
「カカンカカン」で1小節 384 tick、2セットで 768 tick。**他のリズムと同じ2小節。**

**IJEXA だけ高低を打ち分ける**（口唱歌のカ＝8分、カン＝4分。高高／低低低／高高／低低）。
音は分かれている（高 1180Hz・低 790Hz）。
**譜面の書き分けは現状のままで良いと決めた**（2026-08-27 オーナー判断）。
1本線の上下 6.1px しか差がなく音の違いとしては読めないが、
**高低を打ち分けるリズムは今後も IJEXA だけの予定**なので、
書き分けのために譜面の作りを変えるコストに見合わない。

### リズムを足すときに要るもの

口唱歌（カ＝打点、ン＝休み）と拍子・小節数があれば足せる。加えて:

- **出典**（`SourceMeta`）。誰が採譜し、いつ確認したか。画面には出さない
- **反転を許すか**。許すなら `clave: "3-2"` を立てる。
  **打点がクラーベの形（前半3打・後半2打）をしているものだけ。**
  形が違うリズムに当てると、アプリが根拠のないことを主張することになる
- 高低の打ち分けの有無

記譜の約束:

- **音価は拍の境目をまたがない**（タイは v1 で使わないため）。またぐ箇所は分けて書く
- **休符は付点にしない**（2026-09-02 オーナー判断）
- 打楽器の一撃を長く伸ばして書かない

足したら `pnpm gen:golden` で golden を作り直し、`check:notation` を通す。

調査の結論として、**攻撃者から見た脅威モデルは小さい**。外部通信ゼロ、
権限ゼロ、URL スキーム無し、保存するのは最後に選んだリズムの id ひとつ。
リモートからの到達経路が無く、CSP 不在も**現状は侵入経路になっていない**
（codex も同結論）。実在する脅威は次の2つだけ:

1. **サプライチェーン** — npm 依存の汚染 → 開発マシンの署名鍵が盗まれ、
   オーナー名義で署名されたアプリが**知人（BOAVISTA メンバー）の端末に入る**。
   `pnpm-workspace.yaml` の `minimumReleaseAge: 10080` ほか3設定が主要経路をふさいでいる
2. **Apple Developer アカウントの乗っ取り** — 公開後は既存利用者へ更新を配信できる。
   $99 を払って登録するときに、ハードウェア2要素認証まで済ませる

**ただし「攻撃されないから緩くてよい」にはならなかった。**
最も重かったのは、**攻撃と無関係に通常操作で踏むデータ競合**だった。

直したもの（ブランチごとに1件、いずれも `dev` へマージ済み。push はしていない）:

| ブランチ | 内容 |
|---|---|
| `fix/rt-thread-data-race` | ロックが共有状態を守っていなかった。`requestChange` がロック内で読む `renderer` / `currentFrame` / `lastScheduledTick` を、オーディオスレッドはロック外で書いていた。加えて Capacitor はプラグイン呼び出しを専用バックグラウンドキューで実行する一方、割り込み通知は main で届くため、`engine` / `lastPlan` / `title` もキューをまたいで競合していた |
| `fix/audio-observer-lifecycle` | `addObserver(forName:)` の戻り値を捨てており、**再生開始1回につき3個ずつ蓄積**していた。`startEngine` が既存エンジンを止めずに参照を上書きしていた |
| `fix/plan-input-bounds` | `originTick` が未検証（`Int.min` で桁あふれ）、`originSeconds` は `isFinite` のみ（`1e300` が通る）、`cycleTicks` に上限なし（`Int.max` で桁あふれ）。`JSONDecoder` が件数を数える前に配列を丸ごと展開していた |
| `fix/realtime-safe-render` | `hits` がコールバックごとに配列を確保していた。要求が使い回しバッファより大きいとき、時計をバッファ長しか進めておらず音と再生位置がずれていた |
| `fix/output-limiter` | 打点の**密度**が縛れておらず、周期長 1 で毎秒約1280回鳴らせた（歪んだ持続音）。`setVolume(.nan)` が**最大音量**になっていた |

**実装中に `abs(Int.min)` を踏んだ。** 検査そのものがトラップする。
範囲の両端と直接比べる形に直した。まさに直そうとしていた種類のバグだった。
